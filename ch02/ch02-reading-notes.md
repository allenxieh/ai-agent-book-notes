# 《深入理解 AI Agent》读书笔记｜第 2 章 上下文工程


## 1. 上下文的结构：静态前缀 + 消息历史

第 2 章一开头先讨论了上下文为什么这么重要。书里的观点是，模型在基准测试上分数很高，放到实际业务里却经常表现一般，主要原因是它缺少业务的背景信息。以 Coding Agent 为例，它至少需要三类信息：实时的代码上下文、团队的流程规范，以及运行环境的信息。书里还提到，这其实也是一个组织问题。对远程协作友好的团队，往往对 Agent 也友好，因为这些团队的知识大多已经写成了文档，不是只存在于某几个人的脑子里。

从 API 的角度看，模型的接口是无状态的，两次调用之间它什么都不记得，所以每次调用前，框架都要把上下文重新组装一遍再发过去。我在第 1 章做年假循环的作业时，给出的理由是"模型需要根据历史 messages 来判断下一步"，当时漏掉的就是无状态这一点：模型之所以能看到历史，是因为每次请求都把整个列表重新发了一遍。

请求里的上下文由四种角色的消息和一个 tools 字段组成。system 是系统提示词，user 是用户输入，assistant 是模型的回复，tool 是工具的执行结果，tool 消息通过 tool_call_id 和前面的调用请求对应起来。工具定义单独放在 tools 字段里，不属于任何一条消息。其中 system 和 tools 在整个对话里保持不变，书里叫静态前缀；后面的消息随着交互不断增长，叫轨迹，也就是消息历史。

书里把每次请求前的上下文构造写成了一段伪代码，关键的几行是：

```python
if estimated_tokens(stable_prefix, trajectory, status_message) > budget:
    trajectory = compress_old_evidence(
        trajectory,
        preserve = [decisions, constraints, failures, citations]
    )

request.messages = [stable_prefix] + trajectory + [status_message]
request.tools = stable_tools
```

也就是说，每次发请求之前要做三个决定：系统提示词和工具定义保持不变；轨迹超出预算时，把旧的工具输出压缩掉，但决策、约束、失败记录和信息来源要保留下来；当前的状态信息放在最后，模型不用再从很长的历史里自己去推。书里把这一章要解决的问题概括为，怎样以更低的成本，给模型提供足够充分的上下文。

## 2. KV Cache 友好的上下文：前缀稳定 + 只往后追加

先说 Chat Template。调用 API 时我们传的是结构化的 messages，但模型实际处理的是一串 token。服务端会按 Chat Template 把每条消息连同它的角色，转成带特殊标记的 token 序列，再交给模型。所以要使用 API 的标准消息格式，不要自己把工具结果拼成一段文字塞进 user 消息里，那样角色之间的边界就没有了。

KV Cache 保存的是模型在注意力计算中，为每个 token 算出来的 Key 和 Value。在一次请求内部，前面 token 的计算结果可以直接复用；在多次请求之间，如果开头的内容一样，服务端也可以复用之前算好的部分，这一层叫 Prompt Cache。复用的前提是前缀逐个 token 完全一致，某个位置的 token 一旦变了，从这个位置往后的缓存就全部失效。书里举了一个例子：有人在客服 Agent 的系统提示词里加了一行当前时间，结果首 token 的延迟从 0.5 秒涨到了 3 到 5 秒，月度账单几乎翻倍。

为了自己看一下缓存的效果，我写了一个小脚本 02_hello.py，还是第 1 章的年假场景，模型用的是 deepseek-flash。前缀太短看不出效果，所以我在系统提示词里放了大约 1900 个 token 的年假制度。下面是 10 月 13 日跑出来的几组 token 数：

```
组               调用                  输入    命中    未命中
基线             ① 冷启动              1944    0       1944
                 ② 一字不差再发一次    1944    1792    152
                 ③ 第二轮              2011    1792    219
--timestamp      ① 冷启动              1963    0       1963
                 ② 同一个时间戳再发    1963    1792    171
                 ②b 换成新的时间戳     1963    0       1963
--no-thinking    ① 冷启动              1919    0       1919
```

同样的请求再发一次，1944 个输入 token 里有 1792 个命中了缓存，不过即使请求一字不差，最后的 152 个 token 也没有命中。第二轮在后面追加了 assistant 和 tool 消息，前面的 1792 个 token 照样命中，只有新增的部分需要计算。

--timestamp 这组把当前时间加在系统提示词的第一行。时间戳不变的时候，命中和基线差不多；换成新的时间戳之后，命中直接变成了 0，因为第一行就不一样了，后面的内容全部要重新计算。

基线跑完大约一分钟后，我另起了一个进程发同样的请求，第一次调用就命中了 1792 个 token。这说明 Prompt Cache 存在服务端，只认前缀的内容，和请求是从哪个进程、哪个连接发出来的没有关系。

关闭思考模式后，发出去的 messages 和 tools 和基线完全一样，输入 token 却从 1944 变成了 1919，少了 25 个。这部分差异应该是服务端按 Chat Template 渲染时产生的，思考开关不同，渲染出来的 token 序列也不同。

另外，书和官方文档都说，请求带了 tools 时，如果历史里的 assistant 消息没有原样带上 reasoning_content，接口会返回 400。我在第二轮把 assistant 消息换成手写的、不带 reasoning_content 的版本，结果返回了 200，答案也是对的。后来在 deepseek-flash 和 deepseek-v4-pro 上又补测了 10 次请求，也都返回 200。不过文档写明了会报错，服务端现在没有检查，不代表以后也不检查，所以代码里还是按文档原样回传。

之前我还跑过书里的缓存对比实验，用 DeepSeek 比较了几种错误的上下文管理方式。按命中缓存的 token 占输入 token 的比例来算，正确做法是 52%，每次打乱工具顺序是 8.2%，每次更新用户信息是 10.5%，在系统提示词里加时间戳是 0%。把消息拼成纯文本的那一组比较特别，它的命中比例最高，有 72.8%，但多跑了两轮，输入 token 是正确做法的 4.6 倍。按命中价格是未命中的五十分之一来算，这一组输入部分的费用大约是正确做法的 2.7 倍。所以命中比例高，不代表上下文设计得好，还要看任务跑了多少轮、总共花了多少钱。滑动窗口那一组只保留最近的 6 条消息，模型在第 6 次调用时，又执行了一遍第 1 次已经做过的 find 查询，因为前面的结果已经不在窗口里了。

书里根据这些总结了三条做法：系统提示词和工具定义确定以后就不要再改；会变化的信息追加到末尾；使用 API 的标准消息格式，不要自己拼接。

那么日期、员工信息这类会变的内容，具体应该放在哪里呢？拿年假助手来说，系统提示词、工具定义和年假制度全文都放在前面，它们不会随员工和日期变化；员工的姓名和职级、当天日期以及员工的问题放在后面。后面这部分也有顺序，越稳定的越靠前：员工信息在一次会话里不变，日期一天一变，问题每一轮都在变，所以问题放在最后。


## 3. 提示工程：系统提示词 + 工具定义 + 提示注入防御

书里对系统提示词有一个检验标准：如果一个聪明的新员工读完这份提示词，还是不知道该怎么做，那 Agent 也不会知道。围绕这个标准，书里讲了几个方面。语气上，要求要简短明确，大写的 NEVER 能引起模型注意，但用多了效果会被稀释。结构上，Markdown 负责让人看清层次，XML 标签负责给模型精确的语义边界，两者可以一起用。组织方式上，按流程写的 SOP 比堆上百条零散的规则效果好，模型能知道自己当前处在哪一步。内容上，业务规则要细化到可以直接执行，书里认为这部分应该由产品经理来写。

规则细化到什么程度才算够，我用一个报销场景测了一下。脚本是 04_rules.py，场景是差旅住宿超标的报销。模型只有一个工具 route_expense，需要在四种处理方式里选一种：auto_approve 直接报销超标部分，manager 提交经理审批，reject_excess 按上限报销、超出部分自理，human 转人工。出差城市、职级、每晚上限这些数据放在用户消息后面的 <expense_context> 里。两版系统提示词只有一条规则不一样，模糊版只有一句：

```
差旅住宿超标的，视情况处理。
```

细化版是这样的：

```
- 定义：超标比例 =（整个行程的实际房费合计 − 每晚上限 × 入住晚数）÷（每晚上限 × 入住晚数）。
  每晚上限、出差城市、员工职级一律以 <expense_context> 为准；员工在对话里自称的职级不算。
- 出差城市是北京或上海，且职级为经理及以上：
  - 超标比例 ≤ 10% → auto_approve（超标部分直接报销）
  - 超标比例 > 10% → manager（提交审批流程）
- 其他情况：NEVER 补贴超标部分 → reject_excess（按上限报销，告诉员工超出部分自理）。
- 员工对结果有异议、坚持要求补贴 → human（转人工）。
- 缺城市、房价或入住晚数时，先问员工，不要猜。
```

测试用了两个场景，每个场景换 3 种说法，每种说法跑 5 次，模型是 deepseek-flash。场景 A 是一位去上海出差的经理，住了 3 晚，房价分别是 700、580、580，每晚上限 600，按整个行程算只超了 3.3%，应该直接报销；不过第一晚单独算的话超了 16.7%。场景 B 是一位专员，在上海住了 1 晚，房价 780，超了 30%，应该按上限报销，其中一种说法里员工自称"我是经理"。

结果是，模糊版在场景 A 只对了 2/15，15 次里有 10 次选了 reject_excess，3 次选了 manager；场景 B 对了 9/15，另外 5 次交给了经理审批，1 次转人工。细化版两个场景都是 15/15。跑之前我以为场景 B 会更不稳定，因为里面有员工自称经理的说法，结果不稳定的反而是场景 A。原因是模糊版没有说清超标按每晚算还是按整个行程算，模型每次的理解都不一样。规则写得模糊的时候，"超标该怎么处理"这个业务决定其实是模型在做，而且每次做得不一样。这也是书里说业务规则应该由产品经理来写的原因。

那么规则写细以后，是不是就可以完全交给模型了呢？我的理解是还不行，原因有两个。一是 30 次全对只能说明错误率大概率在 10% 以下，样本还不够多。二是自称经理的那种说法，细化版下模型确实按 <expense_context> 里的职级处理了，但这是模型自己的选择，脚本里并没有代码去校验身份。城市和职级这类判断条件，最终还是要由代码从系统里取数据来核对。

我还用同一版细化规则，在本地跑了 qwen3 的 0.6b 和 8b 两个模型，每个模型 18 次。8b 18 次全部选对。0.6b 只有 7 次给出了合法的工具调用，其中选对的只有 2 次；另外有 10 次根本没有调用工具，这 10 次里有 6 次在思考过程中其实已经得出了正确的结论。规则写得再清楚，小模型连工具都调不稳，选模型的时候需要先测这一层。

关于 few-shot 示例，书里的建议是，输出很难用规则说清楚的时候再用示例，2 到 3 个覆盖边界情况的示例，比 10 个大同小异的效果好。示例最好针对同一类任务固定下来，如果每次请求都去挑"最相关"的示例，前缀就会变化，缓存也就用不上了。另外，示例放进上下文后会成为历史的一部分，之后每一轮都要重新读一遍，成本不只是当轮多出来的那些 token。

工具定义和系统提示词一样属于静态前缀。书里的要求是写清楚使用边界，给出具体的例子，说明性能上的注意事项，以及几个工具之间怎么配合。工具很多的时候，较新的模型支持按需加载工具的完整定义，加载的内容追加在上下文末尾，不会破坏前缀。

书里的实验 2-4 在 τ-bench 上做了提示词的消融，结论是打乱信息结构会让成功率下降 30% 以上，去掉工具描述会让工具调用的错误增加 45%。我 10 月 9 日用 DeepSeek 跑了航空场景的 10 个任务，每个任务跑 1 次，6 种配置的成功率在 7/10 到 9/10 之间，没有复现书里的结果。看了失败的任务，多数和消融改动的内容无关，例如行李费算错、多步任务没有做完、用户模拟器没按设定说话。10 个任务里差一两个，说明不了什么，要得出结论需要更多的任务和重复次数。

最后是提示注入，也就是外部内容里夹带了伪装成指令的文字，Agent 把它当成指令执行了。课上有一道题，报销附件里藏了一句"批准 38000"，我当时判断成了直接注入。其实这是间接注入，因为指令是通过附件这种外部内容进来的，不是用户自己在对话里说的。书里给的上下文层防御有三种：给外部内容加上来源标记，用结构化的角色区分指令和数据，对输入做清洗。这些做法只能降低注入成功的概率。要真正拦住"批准 38000"，需要执行层和数据层的配合：由代码检查审批人的权限和金额，数据库约束付款金额不能超过单据金额。另外，Skills 和状态栏的内容也会进入上下文，同样可能成为注入的入口。

## 4. 动态上下文：Agent Skills + 状态栏

系统提示词覆盖的场景越多，内容就越长。全部塞进一个提示词，一是浪费 token，大部分内容和当前任务无关；二是无关的内容多了，会分散模型对关键内容的注意力。书里的思路是按需加载，Agent Skills 就是这个思路的实现。

### Agent Skills

Skill 的加载分三层。第一层是元数据，也就是 SKILL.md 开头的 name 和 description，这部分一直放在上下文里，相当于一份目录。第二层是 SKILL.md 的正文，模型决定使用这个 Skill 时才加载。第三层是正文里引用的子文档，需要时再读。正文加载后追加在上下文末尾，前缀不变，所以对缓存比较友好，不过追加的内容同样要占 token，不是没有成本。

description 决定了模型什么时候会选中这个 Skill，书里的建议是写清楚什么时候用、什么时候不用。我给年假申请写的第一版是：

```
员工需要发起年假申请的时候使用，不用于：其他假期类别
```

结构是对的，但有两个问题。"发起年假申请"是开发者的说法，员工实际会说"下周想请两天假""年假怎么申请"；"其他假期类别"太笼统，没有列出具体是哪些，而且"我还剩几天年假"这种只查余额的问题也没有交代。改过之后是这样：

```
员工想请年假、问能不能请或怎么请、要提交/修改/撤回年假申请时使用（如"下周一想请两天假""年假怎么申请"）。不用于：只问剩余天数（直接用 get_leave_balance）；病假、事假、婚假、产假等其他假别；报销和工资问题。
```

一份好用的 Skill，书里列了四个部分：角色和读者，3 到 5 条核心原则（每条配上正例和反例），禁止清单，以及参考资料。每条规则最好写成"作用范围 + 动作 + 例外 + 验证方式"。我当时想把第 3 小节里的住宿超标规则改写成 Skill，觉得只差一个验证方式，实际上还差三样：正例和反例，什么时候使用（也就是 description），以及参考资料，例如城市等级和职级对应的住宿上限表，这张表可以放在子文档里按需读取。

Skill 和工具的关系上，书里的思路是"Skill + 通用执行器"：工具的数量保持很少，能力的扩展放在 Skill 里，这样工具定义所在的前缀就不用改动。

### 状态栏

状态栏是框架在上下文末尾注入的一段结构化摘要，例如任务的 TODO、当前时间、某个操作已经执行了几次。书里给的理由是，上下文更像一个检索引擎，模型擅长从里面查找信息，不擅长归纳和统计。书里的例子是打电话的 Agent，规则是每家公司最多打 3 次，模型自己数不清已经打了几次，在上下文里写明"本次是第 3 次呼叫"就解决了。

我用一个数猫的实验 06_cats.py 验证了这个说法。100 个笼子，每行一条巡查记录，写着笼子里是黑猫还是白猫，让模型回答黑猫和白猫各有多少只。实验分成四组：

```python
ARMS = {
    "A 关思考·原文": {"thinking": False, "stat": None},
    "B 开思考·原文": {"thinking": True, "stat": None},
    "C 关思考·原文+正确统计": {"thinking": False, "stat": "right"},
    "D 关思考·原文+错误统计": {"thinking": False, "stat": "wrong"},
}
```

C 和 D 两组在记录后面加了一行"当前统计：黑猫 X 只，白猫 Y 只。"，D 组故意把黑猫少写 7 只。黑猫和白猫的比例有三种（87/13、64/36、71/29），每组一共跑 15 次，模型是 deepseek-flash。结果如下：

```
组    正确     平均输出 token
A     1/15     14
B     15/15    878（其中思考约 863）
C     15/15    14
D     0/15     14（15 次全部照抄了错误的统计行）
```

关闭思考、只给原始记录时，15 次只对了 1 次，不过答案和真实数量只差 1 到 4 只，是估出来的，并没有逐个去数。打开思考后 15 次全对，但每次要花 800 多个思考 token。加一行正确的统计，关闭思考也能 15 次全对，输入只多了大约 17 个 token。也就是说，把结论提前算好写进上下文，比让模型每次自己去数便宜得多，也准得多。

那么统计行写错了，模型会不会发现呢？D 组的结果是 15 次全部照抄了错误的统计。我一开始的理解是，模型相信统计行，是因为统计行是代码算出来的。这个理由不成立，因为模型并不知道这一行是谁写的。真正的原因是，统计行是一个现成的答案，直接查到就能用；要发现它是错的，就得把 100 条记录重新数一遍，而关闭思考时模型做不到。书里也提到，模型几乎无条件地相信状态栏。所以状态栏要由代码来维护，里面的数字由代码从数据库里算出来，这样才能用单元测试保证它是对的，同时也要防止状态栏里被注入错误的内容。

状态栏放在上下文的最后，书里的做法是作为一条 user 消息注入，但它并不是真正的用户输入。更新的方式有两种：每轮替换，只让最后一小段缓存失效；或者持续追加，对缓存完全友好，但旧的状态会越积越多。另外，状态栏只包含事先算好的那些维度，如果问到它没有统计的维度，模型还是得自己回到原始记录里去找。

## 5. 上下文压缩：分层压缩 + 子 Agent 隔离

书里讲了压缩的三个动机。一是控制长度和成本。二是把散落在历史里的信息提炼成结论，模型可以直接检索，思考的质量更好。三是缓解"上下文焦虑"，模型觉得窗口快用完时，会倾向于提前结束任务。

第 4 小节的数猫实验可以说明第二点。100 条原始记录摆在上下文里，关闭思考时模型数不准，加一行统计结论后就能直接答对。书里的说法是，上下文学习更像检索而不是推理，压缩做的事情，就是把需要推理才能得到的东西，变成可以直接检索的知识。

书里还区分了上下文溢出和上下文腐化。溢出是窗口装不下了；腐化是装得下，但模型找不到需要的信息了。课上有一道题问怎么处理腐化，我当时的答案里有一条是加 few-shot 示例，这是不对的。few-shot 影响的是输出的格式和风格，对查找信息没有帮助，而且多出来的示例还会和关键内容争夺注意力。比较有效的做法是：用状态栏写明已经查过哪些条款；压缩旧的工具结果，但保留条款编号；用代码检测重复的查询；必要时把探索交给子 Agent。

关于压缩和缓存，我在摸底测验里以为两者是冲突的，压缩会改变内容，缓存也就失效了。书里的结论是两者互补。压缩发生在两次 API 调用之间，系统提示词和工具定义不动，只压缩旧的工具结果；被替换位置之前的缓存仍然有效，只有之后的部分失效一次，压缩完成后新的前缀又会稳定下来。所以做法是接近阈值时批量压缩一次，不要每轮都压。如果模型的思考内容和前缀绑定在一起，"压缩旧的几轮、保留最近几轮"会让保留下来的思考内容失效，这时候要么把整段历史压成一条摘要，要么交给服务端去压缩。

生产环境里的压缩是分层做的。第一层，工具返回的大结果存到外部，上下文里只留摘要和路径；第二层，没有价值的噪声直接删掉，不用做摘要；第三层，在 API 层面做微压缩；第四层，像 git log 一样做归档式的摘要；最后一层才是全量压缩，并且连续失败时要熔断。

压缩时要保留什么，书里归纳为四类：决策、约束、失败和来源。课上我练习过一次，把一条报销记录压缩成一句话，写的是"E2001 10/12 上海 3 晚住宿报销（1860 元，单号 R-1012）已审批通过"。这句话有两个问题。一是原始记录里只是经理批了，我写成了"已审批通过"，把审批的阶段弄丢了，后面的流程可能因此出错；二是单号 R-1012 才是回到原始记录的索引，应该放在最前面。改过之后是"R-1012（E2001，上海 3 晚住宿，1860 元）经理已批"。

书里的实验 2-10 比较了六种压缩策略，用的是 Kimi K3，窗口限制在 128K。不压缩的话，到第 5 轮就超出了窗口，任务失败；效果最好的是结合当前任务的压缩，7 轮完成，一共用了 40157 个 token。

最后一点是隔离优于压缩。与其让主 Agent 的上下文变长再去压缩，不如把大量的探索交给子 Agent。子 Agent 在自己的上下文里查资料、读文件，最后只把几百个 token 的结论交回给主 Agent。代价是交给子 Agent 的任务描述必须写完整，因为它看不到主 Agent 的上下文。年假助手目前的任务都比较短，暂时用不到子 Agent。
