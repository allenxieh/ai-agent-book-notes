# 《深入理解 AI Agent》读书笔记｜第 1 章 AI Agent 入门


## 1. Agent 的组成：LLM + 上下文 + 工具

书里对 Agent 的定义是一个公式：Agent = LLM + 上下文 + 工具。用书里的比喻，LLM 是大脑，上下文是眼睛，工具是手脚。公式看起来很简单，但这三样东西落到代码里分别对应什么，还是要对照实际的请求才看得清楚。下面结合我跑的实验 1-1 分别说说。实验用的是 DeepSeek，任务很简单：让 Agent 调用计算器算 (125 + 375) * 8。

### 什么是 LLM

LLM 负责做决策。简单来说，一次决策就是一次 chat completions 接口调用：传入 messages 和 tools，返回一条 assistant 消息。这条消息只有两种情况：

- 带 `tool_calls`：模型想调用某个工具，并给出了参数；
- 只有 `content`：模型认为信息够了，直接回答。

模型本身不会执行任何东西，也不会记得上一次请求的内容。可以把它理解成一个无状态的接口，它能用的信息只有这次传进去的参数。DeepSeek 的返回里还会多一个 `reasoning_content` 字段，是模型的思考过程。

### 什么是上下文

上下文就是每次请求时传给模型的全部内容。因为接口是无状态的，所以每一轮都要把前面的对话完整地再传一遍。按 API 的结构，上下文由五部分组成：

- `system`：系统提示词，由开发者编写，定义模型的角色和规则
- `tools`：工具定义
- `user`：用户的输入
- `assistant`：模型之前的回复，包括 `reasoning_content`、`content`、`tool_calls`
- `tool`：工具的执行结果

其中前两部分在整个对话中不会变，书里叫静态前缀；后三部分每一轮都会往后追加，叫消息历史。

实验 1-1 第二次请求时传入的 messages 如下（省略了 system 和 tools）：

```json
[
  {"role": "user", "content": "请调用计算器计算 (125 + 375) * 8，并给出结果。"},
  {"role": "assistant",
   "content": "I'll calculate this expression for you.",
   "reasoning_content": "The user wants me to calculate (125 + 375) * 8. Let me use the calculate tool.",
   "tool_calls": [{"id": "call_00_0tBnc...", "type": "function",
                   "function": {"name": "calculate", "arguments": "{\"expression\": \"(125 + 375) * 8\"}"}}]},
  {"role": "tool", "tool_call_id": "call_00_0tBnc...",
   "content": "{\"expression\": \"(125 + 375) * 8\", \"result\": 4000, \"type\": \"int\"}"}
]
```

从这段 JSON 里能看出两个写代码时要注意的细节。

一是 assistant 消息里 `content` 和 `tool_calls` 同时出现了。所以判断循环要不要继续，应该看有没有 `tool_calls`，而不是看 `content` 是否为空。

二是 `reasoning_content` 也要原样传回去。DeepSeek V4 的规定是，只要请求带了 `tools`，历史里的 assistant 消息就必须带上 `reasoning_content`，否则接口直接返回 400。

模型只能根据传进去的内容做判断，没有放进上下文的数据，对它来说就是不存在的。所以当 Agent 答错时，我会先去看 trace，确认需要的信息有没有进到 messages 里，而不是第一时间去换模型。

### 什么是工具

工具是 Agent 跟外部世界打交道的接口。工具定义的特征和我们平时写的接口很像：只声明，不实现。定义里只写工具名、用途和参数格式（JSON Schema），真正的实现是开发者写的执行代码。实验里 `calculate` 的定义：

```json
{
  "type": "function",
  "function": {
    "name": "calculate",
    "description": "Evaluate a simple mathematical expression",
    "parameters": {
      "type": "object",
      "properties": {
        "expression": {
          "type": "string",
          "description": "The mathematical expression to evaluate (e.g., '2 + 2 * 3')"
        }
      },
      "required": ["expression"]
    }
  }
}
```

模型只能看到这份声明，它返回的也只是"调用 calculate，参数是 (125 + 375) * 8"。整个调用过程是这样的：

1. 模型返回工具名和参数；
2. 程序（书里叫 Harness）解析参数，执行对应的代码；
3. 把执行结果作为一条 role 为 tool 的消息追加到 messages 里，`tool_call_id` 要和调用时的 `id` 对上；
4. 带着结果再请求一次模型。

那么既然真正执行的是我们自己的代码，参数校验和权限检查应该放在哪里呢？答案很清楚：写在执行代码里，不能指望模型自己遵守。

书里按交互方向把工具分成了五类：感知、执行、协作、事件触发、用户沟通。其中事件触发比较特殊，它由外部事件（比如定时任务、收到新邮件）唤醒 Agent 开始工作，Agent 自己不会主动去调它。

选工具时，书里给的原则是先从最窄的能力开始。像代码解释器这种通用工具，组合能力很强，但必须放到沙盒里运行；而付款、删除数据这类高风险操作，更适合做成参数明确、权限受限的专用工具。

最后把这次实验串起来看，一共请求了两次模型：第一次模型返回 calculate 调用，程序算出 4000 并追加 tool 消息；第二次模型看到结果，返回 `finish_reason` 为 stop、没有 `tool_calls` 的最终回答。


## 2. Agent 的运行：ReAct 循环

ReAct 是 Reasoning + Acting 的缩写，意思是让模型想一步、做一步、看一眼结果，再想下一步，一直循环到任务完成。书里的例子是把四个季度不同币种的收入换算成美元再汇总，模型一共跑了 3 轮，调了 4 次工具。

落到代码里，ReAct 就是一个 while 循环。做这个作业之前，让我自己写一个 Agent 循环，我其实不知道该写哪些东西。所以我先把需求定下来，让 AI 帮我实现了一个最小版本，再围绕它做了几个实验，把循环里每一步的作用弄清楚。

### 一个最小的 Agent 循环

场景是员工问 HR 助手："我还剩几天年假？"模型用的是 DeepSeek，工具只有一个 `get_leave_balance`，执行时固定返回 `{"remaining_days": 5}`。这个工具没有 `employee_id` 参数，员工 ID 由程序从登录会话里取，模型看不到。这样员工就没法通过一句"我的工号是 xxx"去查别人的余额。

核心循环如下（省略了打印 messages 的代码）：

```python
iteration = 0
while iteration < MAX_ITERATIONS:
    iteration += 1
    response = client.chat.completions.create(model=MODEL, messages=messages, tools=tools)
    assistant_message = response.choices[0].message

    if iteration >= MAX_ITERATIONS and assistant_message.tool_calls:
        print("未能完成，已转人工")
        break

    if not args.drop_assistant:
        messages.append(assistant_message)  # 第 1 处 append：模型的回复，原样放回
    for tool_call in assistant_message.tool_calls or []:
        result = execute_tool(tool_call.function.name, tool_call.function.arguments, SESSION_EMPLOYEE_ID)
        messages.append({"role": "tool", "tool_call_id": tool_call.id, "content": result})  # 第 2 处 append：工具结果

    if not assistant_message.tool_calls:  # 没有工具调用 = 最终回复，退出循环
        print("\n最终回答：", assistant_message.content)
        break
```

整个循环里只有两处 append：一处放回模型的回复，一处放入工具结果。每调一次模型，messages 就往后长一截，下一次请求把整个列表再发一遍。

那么循环靠什么停下来呢？有两种情况。正常情况是模型的回复里没有 `tool_calls`，说明它认为信息够了，返回的就是最终回答。另一种是兜底：调用次数到了 `MAX_ITERATIONS` 还没结束，就转人工，防止出现异常时无限制地请求模型。

### 正常跑一遍

正常运行一共调用了 2 次模型。第 1 次请求只有 system 和 user 两条消息，模型返回一个 `get_leave_balance` 调用；程序执行工具，追加 tool 消息。第 2 次请求带着这 4 条消息发出去，模型返回最终回答：

```
最终回答： 您目前还剩 **5 天**年假。需要我帮您办理休假申请或查询其他假期信息吗？
```

我在每次调用后都把 messages 打印出来，和自己事先手推的结果对比，发现打印出来的多了最后一条 assistant 消息。原因是时间点不同：我手推的是"第 2 次请求发出时"的列表，那时最终回答还没生成；程序打印的是"第 2 次调用之后"的列表，回答已经追加进去了。按这个规律，如果每轮只调一个工具，第 n 次请求发出时 messages 有 2 + 2(n−1) 条，跑了 k 轮工具后，结束时有 2 + 2k + 1 条。

### 调试过程

接下来做了几个实验，故意把循环弄坏，看会出什么问题。

第一个实验是把模型的回复丢掉，只追加 tool 消息，也就是代码里的 `--drop-assistant` 开关。我预测会报错，结果 DeepSeek 直接返回了 400：

```
openai.BadRequestError: Error code: 400 - {'error': {'message': "Messages with role 'tool' must be a response to a preceding message with 'tool_calls' ...", 'type': 'invalid_request_error', ...}}
```

tool 消息必须跟在一条带 `tool_calls` 的 assistant 消息后面，`tool_call_id` 要能对上。少了 assistant 消息，这条 tool 消息就成了没有出处的结果，接口直接拒收。

第二个实验是把两处 append 的顺序调换，先追加 tool 消息，再追加 assistant 消息。这次我预测的是模型会被搞糊涂，一直重复调用工具。实际上请求根本没到模型那里，接口在检查格式时又返回了 400。还是同一条规则：tool 消息不光要有对应的 assistant 消息，顺序也不能反。

这个结果让我分清了两类问题。一类是协议错误：消息格式不对，接口直接返回 400，每次都一样，在代码里改掉、写个单测就能锁住。另一类是模型行为问题：格式没问题，但模型做了错误的决定，这种是随机出现的，要靠多跑几次和做评估才能发现。排查的时候先判断是哪一类，思路会清楚很多。

第三个是读代码时卡住的地方：`assistant_message.tool_calls or []` 里的 `or []`，我一开始没看懂。原因是模型给出最终回答时，`tool_calls` 的值是 `None`，不是空列表，直接 `for x in None` 会报 `TypeError`。`None or []` 的结果是 `[]`，for 循环执行 0 次。书上的代码不需要这个写法，因为它先判断没有 `tool_calls` 就 break，走到 for 循环时 `tool_calls` 一定不是 `None`。

最后一个是轮数上限，这部分是我关掉 AI 自己改的。先把 `MAX_ITERATIONS` 改成 1 跑一次，第 1 轮拿到工具结果后循环就结束了：程序没有任何提示，员工什么也没收到，messages 停在一条 tool 消息上。撞到上限时必须明确告诉用户，所以我加了一个兜底，打印"未能完成，已转人工"。

第一版的判断条件写成了 `iteration + 1 >= MAX_ITERATIONS`，用 1 和 5 测都没问题。但年假这个任务正好需要 2 次调用，按这个条件推一下，`MAX_ITERATIONS = 2` 时员工本来下一次调用就能拿到"5 天"，却会被提前转人工。这是一个典型的差一错误，只测远离边界的值是测不出来的，要专门测刚好卡在边界上的值。

修好后的条件是 `iteration >= MAX_ITERATIONS and assistant_message.tool_calls`，放在模型返回之后、执行工具之前。按 1、2、5 三个值推一遍：1 转人工，2 和 5 都能拿到"5 天"，符合预期。检查放在执行工具之前还有一个好处：撞到上限时，不会再去执行一个结果没人用的工具。查余额这种只读工具无所谓，但如果是提交请假单这种会写数据的工具，就会留下一张员工不知道的请假单。

### 循环跑在哪里

我写的这个循环跑在客户端：调模型、执行工具、追加结果，都是自己的代码在做。书里的实验 1-2 和 1-3 是另外两种情况。Kimi K3 的路径里，搜索工具在服务端执行，但"调用模型 → 追加工具结果 → 再调用"这个循环还是客户端代码在驱动；Responses API 的路径里，搜索、代码执行和多轮编排都在服务端完成，客户端不用自己写这个循环。


## 3. Harness 工程：上下文管理 + 工具接口 + 约束 + 验证 + 纠正

书里在讲生产环境的 Agent 时，用了另一个公式：Agent = Model + Harness。Harness 这个词原本是马具的意思，书里用它指模型之外、Agent 之内的那部分代码，例如组装 messages、执行工具、检查权限、处理异常等。也就是说，除了调用模型的那一行，Agent 里剩下的代码基本都属于 Harness。

需要区分的是 Harness 和环境。拿年假循环来说，`execute_tool` 函数属于 Harness，它背后要查询的 HR 数据库，以及来提问的员工，属于环境。书中用沙箱举了一个例子，沙箱的权限和重置机制属于 Harness，沙箱里被修改的文件属于环境。

书里把 Harness 分成五个要素：上下文管理、工具接口、约束、验证、纠正。其中上下文管理和工具接口负责让 Agent 能完成任务，约束、验证和纠正负责保证它不出错。为了方便理解，我把第 2 小节的年假循环按这五个要素标注了一遍。

### 对照年假循环的代码

下面是节选，去掉了实验用的开关，注释标注了对应的要素：

```python
SESSION_EMPLOYEE_ID = "E1001"  # 约束：员工 ID 从登录会话取，模型看不到

tools = [{"type": "function", "function": {
    "name": "get_leave_balance",
    "description": "查询当前员工剩余的年假天数",
    "parameters": {"type": "object", "properties": {}},  # 约束：没有 employee_id 参数
}}]

def execute_tool(name, arguments, employee_id):  # 工具接口：执行代码
    if name == "get_leave_balance":
        return json.dumps({"remaining_days": 5})
    return json.dumps({"error": f"unknown tool: {name}"})  # 工具接口：未知工具返回错误信息

messages = [  # 上下文管理：初始上下文
    {"role": "system", "content": "你是公司的 HR 助手。需要实时数据时，使用工具查询。"},
    {"role": "user", "content": "我还剩几天年假？"},
]

while iteration < MAX_ITERATIONS:
    ...
    if iteration >= MAX_ITERATIONS and assistant_message.tool_calls:
        print("未能完成，已转人工")  # 纠正：撞到上限，转人工
        break
    messages.append(assistant_message)  # 上下文管理：追加模型回复
    for tool_call in assistant_message.tool_calls or []:
        ...
        messages.append({"role": "tool", ...})  # 上下文管理：追加工具结果
```

上下文管理对应的是 messages 的组装和追加。这部分代码虽然不多，但对结果影响很大。在实验 1-1 中，去掉历史消息后，DeepSeek 每一轮都会重新调用同样的三次换汇，5 轮一共调用了 15 次工具，最后也没有给出回答。

工具接口包括工具定义和执行代码。这里有一个细节是执行出错时的处理：`execute_tool` 遇到不认识的工具名时，返回一段错误信息，而不是抛出异常。这段错误信息会作为 tool 消息追加到 messages 中，模型在下一轮可以看到并调整调用；如果抛出异常，循环会直接中断。模型调用不存在的工具的情况确实会出现，在实验 1-1 中，DeepSeek 就在回复里写过一个不存在的工具名 `currency_conversion`。

约束的原则是能力默认关闭，需要时再显式开放，类似于手机 App 的权限申请。书里的例子是 Claude Code，每个工具默认都需要用户授权后才能执行。年假循环里的约束体现在员工 ID 上，工具定义中没有 employee_id 参数，员工 ID 由程序从登录会话中获取。因此即使员工在对话中说"我的工号是 E2002"，模型也无法用这个工号去查询。如果把员工 ID 作为参数交给模型传递，那么能不能查到别人的数据，就取决于模型是否遵守规则了。

纠正在这段代码里只有一处，就是达到轮数上限时打印"未能完成，已转人工"，避免循环在没有任何提示的情况下结束。

### 关于验证

对照下来可以发现，年假循环中没有验证相关的代码。那么怎么判断 Agent 给出的回答是可信的呢？

实验 1-1 中去掉工具定义的那一组可以说明这个问题。这次运行请求成功，没有报错，循环也正常结束了，但模型返回的内容其实是一段写在正文里的工具调用文本，任务并没有完成。只看程序的运行日志，是发现不了这个问题的。

书里对验证的要求是，安全检查只依据结构化数据，例如工具返回的 JSON 字段，而不依据模型生成的文本，因为文本内容有可能已经被提示注入影响。实验 1-1 的分析脚本里有一个依据性检查，它会提取最终回答中的数字，再到工具结果和题目中查找这些数字的来源。对应到年假场景，就是用工具返回的 `remaining_days` 来核对回答中的天数。

不过这个检查只能判断数字有没有来源。在去掉工具定义的那次运行中，它的结论是 `no_quantities`，也就是模型没有编造数字，但任务实际上没有完成。因此验证需要从多个方面进行，答案是否有依据和任务是否完成，需要分别检查。

### 关于纠正

轮数上限可以保证循环最终停止，但不能避免中间的无效调用。在实验 1-1 中去掉工具结果的那一组，DeepSeek 因为拿不到结果，开始用 `2 + 2`、`print("hello")` 这样的测试值去调用工具，直到 5 轮用完。

书里对纠正的要求是，在确认无法恢复之前不暴露中间状态，例如工具调用失败时先静默重试，不把未完成的结果展示给用户；如果连续失败，就触发熔断，交给人工处理。对应到上面的情况，可以检测重复的调用，或者与任务无关的调用，在达到轮数上限之前就提前中止。

书里还提到了 LangChain 的例子。在 Terminal Bench 2.0 上，LangChain 没有更换模型，只是在 Harness 中加入了检查执行结果、检测重复循环等机制，得分就从 52.8% 提升到了 66.5%（成书时的数据）。

另外，书中指出生产环境中的 Agent，重点已经放在约束、验证和纠正这三项上。以 Claude Code 为例，它的 Harness 中大部分代码是权限分类、熔断、错误恢复等机制，工具本身只占一小部分。对比我写的年假循环，目前只有一条约束和一个轮数上限，验证和更完善的纠正都还没有实现。


## 4. Harness 工程落地的三个决策：选模型、选编排、设护栏

书里在讲完 Harness 的五个要素之后，又单独讨论了三个问题：用什么模型，流程由代码固定还是交给模型决定，护栏放在哪里。书里也说明了，这三件事不属于五个要素本身，不过只要真正做一个 Agent，每一件都需要做出选择。

### 选模型

书里没有推荐具体的模型，因为模型更新太快，给的是选型时要考虑的几个方面。第一是要在自己的任务上测试，不能只看排行榜。第二是绝大多数 Agent 都需要支持思考的模型，只有单步的简单任务例外。第三是输出速度，Agent 每一轮都要等模型输出完才能执行下一步，轮数一多，延迟会累加起来。另外还要考虑多模态能力，以及厂商的使用限制，也就是模型愿不愿意执行、接口有没有开放这个能力、服务条款是否允许。开源和闭源的对比，书里的说法是成书时差距在 6 个月以内，开源模型成本更低，也可以私有化部署。

我目前的实验用的都是 DeepSeek，过程中碰到的几个情况正好对应上面这几点。

请求时我写的模型名是 deepseek-v4-flash，但接口返回的 model 字段是 deepseek-flash。所以记录实验结果时，模型名应该以返回结果里的为准。

DeepSeek 的两个模型在图片理解上不一样。用同一张图片测试，deepseek-flash 能识别出图里的内容，deepseek-v4-pro 则回复看不到图片。同一家厂商的模型，能力也不能想当然，需要自己测一下。

速度方面，实验 1-4 里 DeepSeek 每次改写调用的耗时在 1.8 到 4 秒之间。如果一个任务需要跑 20 轮，光是等模型输出就要将近一分钟。

### 选编排

书里的建议是从简单到复杂：能用一次模型调用解决的，就不用 Agent；步骤可以提前确定的，用工作流；步骤没法提前确定、需要根据结果调整的，才用自主 Agent。

工作流的执行顺序由代码决定，模型只在每个节点里面工作。这样做的好处是流程可控，比如"付款之前不能预订"这类规则由代码来保证，即使某个节点被提示注入影响，影响范围也只在这一个节点里；缺点是遇到流程之外的情况，只能走异常分支或者交给人处理。自主 Agent 就是第 2 小节里的 ReAct 循环，下一步做什么由模型根据结果来决定，适合开放性的任务，但成本更高，错误也会一步步累积，所以一定要设置停止条件。两种方式也可以混合使用。

书里还提醒了一点，Harness 重要并不代表越复杂越好。如果一开始就设计很复杂的工作流，遇到新情况就只能不断加节点，系统越来越复杂，通用性反而越来越差。

我拿服务台的两个场景想了一下。经理审批一笔 5 万元的付款，步骤不能跳过，也不能乱序，适合用工作流来保证。员工问出差的住宿标准，需要查职级、查城市等级、再查对应的条款，步骤其实也比较固定，做成工作流也可以。判断用哪一种，主要看执行路径能不能提前确定。

需要注意的是，工作流的确定性只体现在路径上，节点内部仍然是模型在做决定。实验 1-4 的改写节点可以说明这一点。这个节点负责把用户的大白话改写成文生图模型用的提示词，其中一个需求是"帮我做一张新款降噪耳机的产品海报，主打'深夜独处也清净'这句文案"。DeepSeek 改写后的英文 prompt 里没有这句文案，负面词里反而加上了 text、chinese characters，把文字屏蔽掉了，只在 style_notes 字段里建议后期排版时再加上。style_notes 只是中间结果，在工作流里用户是看不到的。另外，5 个需求在 DeepSeek 上的改写，加上仓库里 Kimi K3 的 5 份记录，一共 10 份改写，负面词里都有 text，应该是照搬了系统提示词里的示例，示例给出的负面词里就列了 text。

书里把这种改写节点叫做适配层，它的作用是弥补文生图模型听不懂自然语言的短板。换成能直接理解自然语言的多模态生图模型后，这个节点也就不需要了。

### 设护栏

书里把护栏分成三层，按被绕过的难度来排列。上下文层管的是模型能看到什么，例如过滤无关的问题、检测越狱和提示注入、做内容审核。执行层管的是模型能做什么，主要做法是给工具标注风险等级，高风险的操作需要经过上下文之外的复核或者人工确认。数据层管的是数据最终能被改成什么样，例如数据库的权限和约束。越往下的层越不依赖模型自己的判断，也就越难被绕过。

上下文层有一个限制，在同一个上下文里，Agent 很难判断自己是不是已经被注入了。因此上下文层只能降低风险，还需要执行层和数据层来兜底。

那么在提示词里写一句"大额付款要谨慎"，算不算有了护栏呢？按书里的分法，这只是上下文层的护栏。以审批付款为例，三层可以分别这样做。上下文层，把付款规则写进系统提示词，外部内容标注来源。执行层，把 approve_payment 标为高风险工具，按金额分级，超过阈值必须人工确认，并且这个判断写在代码里。数据层，在数据库里约束付款金额不能超过单据金额，单据状态只能从待审批改为已批准，审批人 ID 从登录会话中获取，不由模型传参。

第 3 小节里的年假循环，员工 ID 从登录会话中获取，也属于数据层的做法，这样即使前面的防护被绕过，模型也拿不到别人的身份去查询。

另外书里还提到两点。一是护栏也会误拒，评估护栏时除了测试该拦的请求有没有被拦住，也要测试正常的请求能不能完成。二是人工干预，通常在两种情况下触发，一种是重试或操作次数超过上限，另一种是涉及大额退款、付款这类高风险操作。年假循环里撞到轮数上限后转人工，就属于第一种情况。


## 5. 全书结构与设计模式

第 1 章的最后两部分，讲的是全书的结构，以及书里反复用到的几个设计模式。

### 全书结构

书里专门说明了前面两个公式之间的关系。全书只有一个骨架，就是 Agent = LLM + 上下文 + 工具，章节也是按它来组织的：第 2 到 6 章讲怎么构建 Agent，第 7 到 9 章讲怎么评估和持续改进，第 10 章讲多个 Agent 之间的协作。Agent = Model + Harness 是这个骨架在生产环境下的展开，它把上下文和工具细分成五个要素，只用在构建这一部分。

五个要素和构建部分的章节是对应的。上下文管理对应第 2 章，跨会话的部分，也就是用户记忆和知识库，对应第 3 章；工具接口和约束对应第 4 章；验证和纠正对应第 5 章。第 6 章讲的是交互，扩展的是观察和动作空间本身，不属于五个要素中的任何一个。安全没有单独成章，而是按第 4 小节里的三层护栏，分散在各章里讨论。

### 设计模式

书里在第 1 章末尾给五个设计模式下了定义。我试着在自己做过的作业里找了找对应的例子。

提议者—审核者，指的是产出和评判由两个角色分别负责，两者不共享上下文，评判方只看产物本身，不看产出方的推理过程。这样设计的原因是自己审查自己不可靠，同一个上下文里的模型，很难发现自己的盲点。实验 1-1 的分析脚本可以看成这个模式的一个简单版本，审核方是一段程序，它判断答案有没有依据时，只看 messages 里的工具结果和最终回答，不看模型的思考过程。

渐进式披露，指的是不把所有信息一次性放进上下文，而是先给一份可以检索的目录，需要时再加载具体内容。这样既节省上下文的空间，也让模型更容易选对需要的信息。书里举的典型例子是 Agent Skills，元数据一直放在上下文里，正文用到的时候才加载。

只增不改，指的是状态只往后追加，已经写下的内容不再修改，这样可以缓存、可以重放，也方便审计。第 2 小节的年假循环里，messages 只有两处 append，从来不改前面的消息，用的就是这个模式。它带来的一个直接好处是缓存。环境运行截图那次请求，751 个输入 token 里有 512 个命中了缓存，因为请求开头的这部分内容和之前的请求相同，不用重新计算。我在另一个实验里试过，在系统提示词里加一个每次都会变的时间戳，4 次请求命中缓存的 token 数都是 0。

边界集 + 保留集，指的是每次修改都要在两批样本上验证，一批是这次修改应当改变结果的样本，另一批是不应当受影响的样本。只测前一批，可能把过拟合当成改进；只测后一批，可能把无效的修改当成安全。第 2 小节修轮数上限那个差一错误，就可以按这个思路来验证。MAX_ITERATIONS 等于 2 属于边界集，按代码推，修复前会提前转人工，修复后应该拿到"5 天"；等于 1 和 5 属于保留集，修复前后的结果都不应该变化。

最小 diff + 可回滚，指的是每次修改尽量小，注明来源，并且可以单独回滚，这样出了问题能定位到是哪一次改动造成的。修那个差一错误时，我只改了判断条件和它所在的位置。书里还提到，第 1 章介绍 LLM 时讲的三条更新路径，也就是上下文适应、更新外部产物、更新模型参数，正是按可回滚的程度从高到低排列的。
