# 《深入理解 AI Agent》读书笔记｜第 3 章 用户记忆和知识库


## 1. 用户记忆：放哪里 + 怎么存 + 存什么

第 3 章开头先分了两个尺度。用户记忆针对单个用户，记的是这个人的偏好、习惯和需求；知识库面向所有用户共享，比如行业法规、公司流程、技术文档。书里的说法是，前者让 Agent 成为"懂你的助手"，后者让 Agent 成为"领域专家"。两者是同一个问题的不同尺度，底层技术大量共用，碰到的麻烦也一样：信息冲突、知识过期、检索不准。和第 2 章比，这一章管的是对话结束以后的事。

用户记忆不是把每句对话都存下来，而是对话结束后再调一次 LLM，提取以后用得上的事实。书里的例子是一段订机票的对话，提取结果是：

```text
- 用户偏好靠窗座位（偏好）
- 用户吃素，航班上需要特殊餐（饮食限制）
- 用户的 United MileagePlus 号码：12345678（会员信息）
- 用户近期有去东京的行程（近期活动）
```

提取要满足三条规则：选择性，丢掉"搜索返回 3 个选项"这类只对当次有用的细节；抽象化，把这一次选了靠窗归纳成长期偏好；结构化，用可以检索的字段来存。

### 先定评估标准

书里在设计之前先定了标准，把记忆能力分成三层，本章后面的实验都用它来衡量：

- 基础回忆：用户直接给的明确信息，比如"我的会员号是 12345"，需要时能准确取回。
- 多会话检索：信息分散在不同时间、不同对象的会话里，要全部找出来再判断。例如用户有两辆车，说"为我的车预约保养"，要找出两辆车的信息，再问是哪一辆，而不是随便猜一辆。
- 主动服务：没有明确指令时，从很久以前的记忆里发现关联，比如订国际航班时，想到几个月前存过的护照快过期了。

实验 3-1 按这三层各做了 20 个用例。被测 Agent 每处理一个会话就更新一次记忆，期间不能回看原始对话，最后只凭记忆回答问题，再由另一个 LLM 打分。

### 放哪里：轨迹和长期记忆

轨迹就是第 1 章说的消息历史，按时间往后追加，原始记录不改；用户长期记忆是跨会话提炼出的稳定信息，通常和用户 ID 绑定，Agent 通过工具调用来读写，内容会被反复改写、合并、淘汰。书里的比喻是，前者是流水账，后者是档案。有些 Agent 还有业务状态，比如"等待付款""请求完成"这类任务阶段。

### 怎么存：四种格式和可执行代码

书里给了四种存储格式，从简单到复杂：

- Simple Notes：每条是一个不可再分的事实，开销最低，但信息之间的联系全丢了，"在 TechCorp 担任高级工程师，负责推荐系统开发"会被拆成三条互不相关的事实。
- Enhanced Notes：每条是一段带上下文的话，语义完整，但同一信息会在多处重复，改一个属性要改好几处。
- JSON Cards：按类别、子类别、键值三层嵌套，可以只改一个字段，但前提是信息能清楚归类。
- Advanced JSON Cards：每张卡片再记下来历（backstory）、说的是谁（person）、和用户的关系（relationship）和时间。它解决的是消歧，同样是"张医生"，可能是用户自己的牙医，也可能是用户父亲的心脏科医生。

书里的选择标准是：关键且少量的信息，比如偏好和人物关系，用 Advanced JSON Cards；大量且不关键的对话事实，用 Simple Notes 降低成本；多数生产系统混用。实验 3-2 的观察也一致：Simple Notes 能过第一层的多数用例，到了需要区分同名实体、跨会话关联的第二、三层就经常失分。

四种格式都是文本，聚合统计、冲突检测这类事最后还是靠 LLM"心算"。书里介绍的 User as Code 换了思路：用户状态存成带类型的对象，规则写成函数，状态一更新就自动检查。比如护照有效期：

```python
for trip in state.trips:
    if trip.is_international:
        days = date_difference(state.passport.expiry_date, trip.departure_date)
        if days < 180:
            alert("passport expires too soon", trip, days)
```

存储上用的是"预写日志 + 检查点"：事实先追加进只增不改的日志，再定期从日志重建状态，原始证据和可执行的状态都保留了。

### 存什么：情景、语义、程序记忆

书里还借了认知科学的分类。工作记忆对应上下文窗口；长期记忆分三种：情景记忆是具体发生过的事，比如"用户订了下周五去东京的 ANA 航班"；语义记忆是提炼出的稳定特征，比如"用户是素食者"；程序记忆是行为流程，比如用户每次订机票都是先搜直飞航班、确认座位偏好、使用常旅客号码，再订餐。

到这里一共有三套分类：记忆层次回答"存在哪里"，存储格式回答"怎么存"，认知类型回答"存什么"。三者是正交的，可以自由组合。


## 2. 记忆的维护：Mem0 与 Memobase + 压缩整理 + 日志脱敏

书里用两个开源框架说明设计取舍。

Mem0 的演进最值得看，它把处理冲突的时机从写入时挪到了检索时。2025 年的论文和 v2 在写入时处理：抽出候选事实后，检索相近的已有记忆，再让 LLM 选择新增、更新、删除或不操作。用户先说住在北京、后来说搬到上海，系统就把前一条更新掉。好处是记忆库简洁一致，风险是一次错误的更新或删除会把历史永久丢掉，而且每条事实都要多一次检索和一次 LLM 判断。2026 年 4 月的 v3 改成只追加，两条带时间的事实同时保留，查询时再综合语义、BM25 关键词、实体匹配和时间来排序，找出当前有效的那一条。Mem0 报告的 LoCoMo 得分从 71.4 提高到 92.5（成书时的数据）。

Memobase 专注于用户画像：画像是开发者配置的一组槽位，存稳定属性；事件记忆按时间线记录经历，回答"我们上次讨论预算是什么时候"这类问题。对话先攒在缓冲区，攒够了再统一提取一次，摊薄 LLM 的调用成本。

书里的看法是，实际框架往往只覆盖一两种记忆类型，按业务需要取舍，比追求大而全更实际。

记忆一直累积，存储会爆炸，检索也会变差。书里给了三层压缩：按访问频率、时间衰减、情感强度、信息独特性打分，低分的压缩或删除；把相似的记忆聚类，每组生成一条摘要，原始记忆存档；从多条情景记忆里提炼出一般规律，变成语义或程序记忆。

隐私方面，实验 3-3 用本地的 Qwen3 0.6B 小模型做日志脱敏，理由是日志本身可能含有敏感信息，发到云端脱敏就违背了初衷。它能识别证件号这类结构化信息，也能识别"我的密码是 abc123"这种自然语言里的敏感内容。书里说召回率在 95% 以上，误报比正则少；吞吐量很大时，可以先用正则过滤明显的模式，剩下的交给 LLM。


## 3. RAG 基础：分块 + 稠密/稀疏检索 + 融合与重排

记忆多到成千上万条后，怎么找到相关的那几条，就是 RAG 要解决的问题。RAG 的流程是检索相关片段，注入上下文，再让 LLM 生成答案。模型的训练数据有截止日期，知识库可以随时更新。

### 分块

文档入库前要先切块：嵌入模型对长度有限制，整篇文档压成一个向量，多个主题混在一起哪个都表达不准；而且块太大，会把无关内容带进上下文。常见的切法有固定大小切分、按标题和段落的递归切分（生产中最常用的默认做法）、按语义断点的语义切分。块太小信息不完整，"该公司收入增长了 3%"不知道说的是谁；块太大主题混杂，检索精度下降。书里给的起点是每块 256 到 1024 个 token，相邻块重叠 10% 到 20%，再按效果调。不管怎么切，块都会和原文的上下文断开，这个问题留到后面解决。

### 稠密检索和稀疏检索

稠密检索把文本转成向量，意思相近的文本向量也相近，用余弦相似度比较，看的是方向而不是长度。早期的 Word2Vec 给每个词一个固定向量，分不清"bank"是河岸还是银行；BERT、BGE-M3 会参考整句话生成向量。数据量大时要用 ANN 索引加速，实验 3-4 对比了两种：ANNOY 构建快、内存小，但数据一变就要整体重建；HNSW 精度更高、支持增量插入，内存占用也更高。

稀疏检索是关键词精确匹配，基础是只看词频、不看顺序的词袋模型。TF-IDF 的直觉是，一个词在当前文档出现得越多、在整个语料里越少见，就越重要。BM25 在此基础上加了词频饱和和长度归一化：重复出现的边际贡献越来越小，长文档也不会因为字多而占便宜。实验 3-5 里查询"模型蒸馏"，某篇文档中"蒸馏"只出现 3 次、"模型"出现 5 次，但"蒸馏"贡献的分数更高，因为它更稀有。稀疏检索擅长技术代码、人名这类查询，但读不懂同义词。

### 融合与重排

两种检索各有盲区：稠密检索搜"HTTP-403"可能返回泛泛的服务器错误讨论；稀疏检索搜"kitty"找不到只写了"cat"的文档。所以生产中两路都跑，流水线分三步：

1. 并行检索：两个引擎各自召回候选。
2. 结果融合：两路分数尺度不同，没法直接比。常用倒数排名融合（RRF），只看排名，得分是 Σ 1/(k + rank)，k 一般取 60。
3. 重排序：用跨编码器对靠前的候选（比如前 50 个）逐个精确打分。

书里特别强调，重排序不是为了弥补 RRF 丢掉的分数信息才加的，而是因为它换了一种更强的匹配方式。检索阶段的双编码器让查询和文档各自生成向量再比较，快但粗；跨编码器把两者拼在一起送进模型逐词比对，慢但准。书里的比方是，前者像猎头筛简历，后者像面试官逐个深谈。

衡量检索质量用三个指标：recall@k 看该找的是否出现在前 k 个结果里，最贴近 RAG 的需求；MRR 看第一个相关结果排得够不够靠前；nDCG 看整个排序的质量。书里脚注说明，这里的 recall@k 其实是命中率，和学术上的定义不完全一样。


## 4. 知识的组织与更新：先提炼再索引 + 结构化索引 + 文件系统 + PR 式更新

### 原始案例直接入库是不够的

书里用两个例子说明，原始材料不加处理地放进知识库，检索做得再好也不够。

第一个是数猫。知识库里有 100 个独立案例，90 只黑猫、10 只白猫，用户问比例。检索只取前 20 条，模型只能根据看到的十几条得出错误结论。如果建索引时预先生成一条摘要"共有 100 只猫：90 只黑猫（90%）和 10 只白猫（10%）"，一次检索就够了。

第二个是 Xfinity 的优惠资格。知识库是几百条客服工单，每条只记一个个案：退伍军人通过了，医生拿到了折扣，教师不符合条件。护士来问自己能不能享受优惠，会碰到三重障碍：一是"护士"和"医生"语义最近，模型顺势推断护士也可以，换一种排序又可能得出相反的答案；二是"仅限……，其他一律不适用"这种边界不在任何一条工单里，调大 k 也没用；三是模型不知道自己有没有看全，于是不追问就自信地回答。解决办法是离线通读整个工单库，提炼出一条带边界的规则卡。

结论是：无论放进向量库还是直接塞进长上下文，没有提炼过的知识，模型都没法可靠地利用。要在建索引时多花计算，把个案压成统计摘要，把散落的个案提炼成规则。

### 结构化索引：RAPTOR 和 GraphRAG

RAPTOR 自下而上建一棵树：把文本块按语义聚类，用 LLM 给每组写摘要作为父节点，再对父节点重复这个过程，最后形成从细节到概括的层次，检索时可以在不同层次上找。

GraphRAG 把知识建成实体和关系的图。它的强项一是多跳推理，"我的医生所在医院的地址"可以沿着关系一路查过去；二是实体消歧，两个同名的"张医生"在图里是两个不同的节点。但书里不建议把它当作用户记忆的通用方案：自然语言转成三元组会丢失语义，"如果下周还下雨，我就取消去海边的计划，改成去博物馆"拆完只剩两个孤立的计划，条件关系没了；提取出错还会污染知识。推荐的做法是核心信息用自然语言保存，加结构化元数据做索引，在医疗、法律这类需要多跳推理的场景再把图谱作为专门的索引。

那么什么时候才需要结构化索引呢？书里的标准是：查询主要是"找到包含某信息的文档片段"，比如"退款政策是什么"，混合检索就够了；经常需要跨文档综合，或者从整体逐层深入到细节，才值得投入，因为它在建索引和查询时都要多调很多次 LLM。实验 3-7 的结论是，RAPTOR 适合从概念钻进细节的问题，GraphRAG 适合"A 和 B 之间是什么关系"的问题，两者组合使用通常更好。

### 文件系统范式

火山引擎开源的 OpenViking 把记忆、资源、技能都映射成虚拟文件系统里的文件。资源写入时自动生成三层：L0 是约 100 token 的一句话概述，用来判断相不相关；L1 是约 2000 token 的概览，供 Agent 决策；L2 是全文，需要时才加载。大部分查询读到 L1 就够了，这和第 2 章 Skills 的渐进式披露是同一个思路。用 Markdown 而不是数据库来存，好处是人能直接读和改，能用 Git 做版本管理和回滚，Agent 也能在分支上自己整理知识，审核后再合入。

前提是文件之间要有链接和索引。互不引用的文件平铺在目录里，知识越多越难找。书里建议组织得像 Wikipedia，提到其他条目就链接过去，再配上入口页和索引页。不同模型主动建链接的意愿差别很大，所以写知识的提示词里要明确要求：新增条目时先链接相关的已有条目，再更新索引页。

### 知识的更新：增量 PR + 定期整理

书里认为更新要有两条路径：事件触发的增量更新，和周期触发的全量整理。

增量更新的做法是把知识库当成代码库，每次知识变更是一个 Pull Request，用第 1 章的提议者—审核者模式：Proposer 从原始证据里发现新事实或冲突，先检索相关的已有知识，再在工作分支上提交一个小而完整的 diff；Reviewer 拿着 diff 和原始证据独立核查，不通过就给出指向具体证据的修改意见；双方迭代到 Reviewer 批准才合入，超过次数上限就转人工，不能默认放行。合入后，再从这个版本重建索引。索引只是可以重建的派生物，Git 里审核过的知识才是来源。

书里对两个角色还有几点要求：两者都必须是能自己搜索、追溯证据的 Agent，而不是两次固定的 LLM 调用；最好用能力相近、来自不同家族的模型，比如一个 Claude、一个 GPT，减少在同一处犯同类错误；权限分开，Proposer 只能写工作分支，只有合并流程能更新主分支和线上索引。

增量更新每次只看到局部，长期下来仍会累积出全局问题，比如同一事实散落多处、新旧说法并存。所以还要定期全量整理：去重、合并、重建链接；回到原始数据核查，而不是在摘要之间互相改写，否则早期的误读会一代代传下去；遇到矛盾的说法，追溯各自的来源，看是不是在不同条件下各自成立，成立就把适用场景写清楚，证据不够就标为待确认，不能简单地保留最新的一条。整理的结果同样走 PR 审核。

最后两点补充：被新版取代的旧内容要带上失效时间，在检索时过滤掉，否则新旧版本会一起被召回；多用户共享的知识库，检索必须按调用者的权限过滤，越权文档一旦进了上下文，就很难保证不泄露。


## 5. 检索进阶：智能体化 RAG + 上下文感知检索 + 双层记忆

### 智能体化 RAG

传统 RAG 是一条单向管道：问题直接拿去检索，结果直接放进上下文，模型直接回答。智能体化 RAG 把检索做成一个工具，交给 Agent 在 ReAct 循环里用：想清楚查什么，检索，判断信息够不够，不够就换个查询再查。书里的比方是，前者像在图书馆只能搜一次就得写报告，后者像研究员可以反复查阅、交叉验证。

实验 3-8 用司法问答做了对比。"正当防卫是怎么规定的"这类简单问题，传统 RAG 更快，质量差不多。"醉酒过失致人重伤且有盗窃前科如何量刑"这类复杂问题，传统 RAG 第一次的关键词不准，常常漏掉关键信息；智能体化 RAG 先拆成几个子问题并行检索，发现缺少把它们串起来的信息后，再针对"累犯""数罪并罚"做第二轮检索。代价是响应变慢。

RAG 也带来了安全问题：检索到的文档是间接提示注入最典型的载体，攻击者可以把恶意指令藏进会被收录的网页或文档里。书里的防御有两层：给检索内容做来源标记，告诉模型这是参考资料，不是命令；转账、删除这类高风险操作，不能仅凭检索内容就执行。

### 把检索用到用户记忆上

实验 3-9 把用户的对话历史本身当作知识库，每 20 轮切一块建索引，给 Agent 一个 search_user_memory 工具。两辆车的例子里，第一次搜索可能只找到本田的记录，Agent 在里面发现用户提过还有一辆特斯拉，于是再搜一次，最后反问用户指的是哪一辆。但另一个用例暴露了局限：妻子设了一笔转账，丈夫在另一通电话里改了，妻子又改了回来。对话块是孤立切出来的，检索到的是三条互相矛盾的指令，判断不出哪条最终有效。

### 上下文感知检索

问题的根源还是分块。Anthropic 提出的上下文感知检索（Contextual Retrieval），是建索引前先用 LLM 给每个块生成一段前缀，说明它的来历，比如"本段内容节选自 ACME 公司 2025 年 Q2 财务报告的'关键业绩指标'章节"，再和原文拼起来建索引。这样稀疏检索多了可以精确匹配的关键词，稠密检索的向量也带上了背景。书里提醒不要和第 2 章的上下文感知压缩混淆：前者在建索引时给块补背景，是加法；后者在运行时裁剪对话历史，是减法。

代价是每个块多一次 LLM 调用，借助 prompt caching，大约每百万文档 token 1 美元。按 Anthropic 的数据，结合 BM25 能把检索失败率降低 49%，再加重排序能降低 67%（成书时的数据）。用到转账的例子上，三个块分别带上了"妻子 Patricia Thompson 正在设立初始电汇""丈夫 James Thompson 正在修改之前的电汇""妻子在丈夫修改后再次修改电汇"这样的前缀，Agent 就能判断哪条最终有效。

### 双层记忆

第三层的主动服务，书里的方案是双层记忆：用 Advanced JSON Cards 把少量关键事实常驻在上下文里，比如护照的到期日；再用上下文感知检索按需取回原始对话的细节。Agent 在卡片里看到一月的东京行程和二月到期的护照，发现日期很近，再检索原始对话确认，最后主动建议加急续签。

书里解释了第三层为什么最难：它同时需要全局概览和精确细节。只靠常驻上下文，细节放不下；只靠检索，发现不了跨会话的关联。本章前半部分的用户记忆和后半部分的知识库，到这里汇合到了一起。


## 6. 知识发现与多模态记忆

第 3 章的最后两部分，讲的是从案例数据里提炼知识，以及多模态记忆。

在很多专业领域，知识藏在大量案例里，比如判决取决于法官如何权衡各种情节，这些经验更多体现在判例中而不是法条里。实验 3-12 分两步做：先让 LLM 分析几百个样本，自由列出影响判决的因素，整理成数据模式，再把每个案例转成标准化的 JSON；然后把案件转成数字做聚类，找出"轻微口角引发的徒手斗殴致人轻伤"这类案件原型，得到因子重要性的层次模型。用户描述案情时，Agent 按因子的重要性依次追问，再基于最相似的原型给出典型刑期范围。书里的结论是，知识库不只是检索的仓库，Agent 可以先把数据读懂，提炼出决策逻辑再来回答。

多模态记忆存的是人脸、声音这类很难用文字描述的信息，书里说还处在学术前沿，介绍了三种思路：存原图加文字描述，检索到描述后再读原图比对；把嵌入存进上下文，每张人脸只占 1 个 token，1000 token 的区域能放 1000 张脸；把信息写进模型参数，比如 User as Engram 把信息写进 Engram 模型的哈希槽位，扩展性更强，但需要模型本身支持，查准率也可能不如前一种。
